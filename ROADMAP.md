# Roadmap

Tracking what's done, what's planned, and what's still undecided for this fork.

## Done / working

- Dynamic tiling (dwindle + master) — inherited from upstream Hypr, unchanged
- Multi-monitor support — verified end-to-end (bar on every screen, correct per-monitor workarea reservation)
- Workspaces — global pool model; switching pulls a workspace to the focused monitor
- Built-in status bar removed in favor of an external EWMH shell (Quickshell)
- Quickshell rofi-style app launcher (usage-sorted results, icons)
- Quickshell bar (workspaces, clock, system tray, CPU/GPU temp, network status, volume)
- Audio (pipewire / pipewire-pulse / wireplumber) autostart on session launch
- Window rules extended with `title:` matching (upstream Hypr only had `class:` / `role:`)
- Fullscreen window rule for Steam games — confirmed working live on two different games. The mechanism turned out to already be fully implemented upstream (`windowrule=fullscreen,class:...`), just undocumented. Steam sets `WM_CLASS` to `steam_app_<appid>` for any game it launches (native or Proton/Wine), so `windowrule=fullscreen,class:^steam_app_.*$` covers a user's whole Steam library with one rule — activated as the default in both the example config and the user's own.
- Launcher positioning — added a new `center` window rule (reuses the existing dialog/modal auto-centering math, now available to any window via config) and applied it to the launcher; verified it lands pixel-exact in the center of the screen
- Animations fix — the animation speed formula (`1/DELTA`) used an integer-truncated millisecond delta; any two ticks landing under 1ms apart truncated to exactly `0`, causing a division-by-zero (infinite speed) that silently stalled that frame. Measured this actually happening (~1 in 221 idle ticks). Switched to a fractional-millisecond delta; confirmed empirically over hundreds of ticks that the stall case no longer occurs.
- Raised the default animation speed to near-instant (`speed`/`window_resize_speed` both 5→20, now equal) per feedback, updated everywhere a default lives (in-code fallback, autogenerated first-run config, example config) so this is the out-of-the-box experience, not just a personal tweak.
- Launcher auto-focus — floating windows (launcher, dialogs, etc.) never actually got X11 input focus from the WM on creation, only tiled windows did; you had to click in manually. Fixed and verified live (docks/panels correctly excluded, so the bar doesn't steal focus).
- Fixed a near-freeze on launching a game: `_NET_WM_STATE_FOCUSED` was appended to a focused window's state property on every dirty-refresh tick with no dedup, growing unbounded for any window that stays busy/dirty while focused (exactly what a game does). Same bug family as the earlier `_NET_WORKAREA`/RandR loops. Verified fixed under a forced stress test (40 rapid dirty cycles → still exactly one entry).
- Fixed focus-stealing (confirmed resolved live, not just in sandbox testing): launching a game and clicking away to another window would immediately snap focus back to the game. Took five attempts to actually nail: a 1s cooldown broke because the real reclaim happened 7+ seconds later; tracking "the specific window the user moved away from" broke because `eventEnter` fires on every window the pointer passes through en route, not just where it settles; the "does current focus belong to the user" redesign still failed live because it explicitly trusted EWMH's own source==2 ("explicit user action") indicator - confirmed via diagnostic logging that Wine/Proton sends exactly that value for its own internal reclaims, making the trust carve-out a complete no-op against the real culprit; one more asymmetry bug (a user hover into an already-focused-for-other-reasons window wasn't upgrading its status) surfaced during re-verification. Final version trusts no EWMH source value at all - only real clicks/hovers count as user-initiated. The live session's own log now shows real reclaim attempts from the game being rejected during actual gameplay, and the user confirmed focus behaves correctly.
- Bug fixes along the way: missing `xcb-util` build dependency, dock/workarea reservation race at map time, an EWMH `_NET_WORKAREA` infinite-loop freeze, a RandR screen-change notification feedback loop, and a broken session launcher that was silently running a stale system-wide binary instead of the real one
- Fixed popup/dropdown menus instantly closing on click or hover (reported live via Zen Browser's bookmark folder menus, "like a double click really fast"). `eventEnter()`'s fallback for a never-before-seen window unconditionally tried to manage and focus it, unlike `eventMapWindow()` which already skips override-redirect windows via `shouldBeManaged()` — toolkits create menus/dropdowns override-redirect specifically so the WM leaves them alone, and stealing focus the instant the mouse entered one made the toolkit immediately dismiss it. Reproduced end-to-end in a Xephyr sandbox against a real Zen Browser instance (clicking a bookmark folder, then hovering an entry inside it to open a nested tooltip) before and after the fix to confirm it.
- "Stay awake" toggle — a bar icon (coffee cup) that toggles X11 screensaver/DPMS blanking on/off via `xset`. No external tool (`caffeine`, etc.) was worth pulling in: this WM runs no idle-lock/screensaver daemon at all (no `xautolock`/`xss-lock`, nothing under OpenRC), so there's no DBus screensaver service for such a tool to talk to anyway — `xset` is the whole mechanism regardless. State lives in a shared `StayAwakeState` singleton so all monitors' bars agree, since DPMS/screensaver state is global to the X server, not per-monitor. Hit and fixed one bug along the way: attaching a `QtQuick.Controls` `ToolTip` (as an attached property) to the same `Item` as a click-handling `MouseArea` silently ate the click events — confirmed via a `console.log` in `onClicked` never firing even though the icon's hit-region was pixel-verified correct; removing the `ToolTip` fixed it immediately. Verified live: clicking each monitor's icon toggles real `xset` DPMS/screensaver state and all three bars' icons stay in sync.
- Configurable bar modules + a "hidden tray" overflow flyout. Hand-edited at `~/.config/quickshell/modules.json` (JSON, not TOML — Quickshell has no TOML parser but reads JSON natively via `JsonAdapter`), hot-reloaded live (no `qs` restart). Each of the 7 status modules (kernel/cpu/cpuTemp/gpuTemp/network/volume/stayAwake) gets `enabled` (on/off), `screens` (`"all"` / `"primary"` / an array of exact RandR output names), and `tray` (`false` = shown inline in the bar as today; `true` = still active, but tucked into a "..." flyout instead of taking up bar space). Checked Noctalia Shell and DankMaterialShell (both Quickshell-based) for prior art first: neither has the "active but tray-hidden" third state at all, just enabled/disabled — this is a genuine addition, not a port. Adapted Noctalia's simpler `enabled` + per-monitor-match TOML model over DankMaterialShell's much heavier full-GUI-settings-app approach. The flyout itself (`Overflow.qml`) needed the same `windowrule=float,title:...` / `windowrule=center,title:...` treatment the launcher already needed — Quickshell's `FloatingWindow` doesn't self-position under this WM by default, it gets auto-tiled like any other window unless a window rule says otherwise. Verified live: toggling `tray` in the JSON hot-swaps a module between the bar and the flyout with no restart, the flyout opens correctly sized and floating (not tiled), and clicking a module inside the flyout (tested with stayAwake) drives the same shared state a bar-inline instance would.
- GUI settings window (`Settings.qml`, gear icon in the bar) for the same `modules.json` the point above covers — a scoped-down first slice of the deferred full GUI settings app, not the whole WM config (that stays hand-edit-only in `hypr.conf` for now). Per-module Enabled / Screens (All or Primary — pinning to specific monitors by name is still JSON-only) / In-tray toggles, built from plain `Rectangle`/`MouseArea` rather than `QtQuick.Controls` (given the `ToolTip` bug found while building the stay-awake toggle, stuck to the pattern already proven reliable in this codebase). Writes go through the same `FileView`/`JsonAdapter` `ModulesConfig` already used for reading, via full-object reassignment (`Object.assign`) rather than in-place mutation, since QML only notices property *assignment*, not a nested object's field changing — confirmed in-place mutation would have silently failed to persist or update any binding. Verified live end-to-end: toggling a module's tray switch in the GUI immediately updates the bar, the flyout, and the on-disk JSON.
- Idle-based screen lock. `xautolock` (idle timer, `exec-once` in `hypr.conf`) driving `betterlockscreen` (a wrapper around `i3lock-color`, both already installed) as the locker, plus a manual `SUPER+L` keybind. No systemd/logind on this box, so `xss-lock` — which leans on logind's Lock/Unlock DBus signals — wasn't the right fit; `xautolock` has no such dependency. Locks after 10 minutes idle (matching the default DPMS timeout) with the desktop wallpaper blurred behind the prompt, cached once via `betterlockscreen -u <path> --fx blur`. Hit one gotcha: `betterlockscreen -l` takes exactly one effect name matching a cached variant, not a comma list — `-l dim,blur` silently fell back to the plain, unblurred image since "dim,blur" isn't a real cached name (confirmed by checking `~/.cache/betterlockscreen/current/`, which only ever holds one file per single effect, never a combined one). Verification was necessarily two-tier given a real i3lock unlock needs the actual account password, which nothing here can supply: the visual rendering (wallpaper/blur, clock, greeter text) was confirmed in a Xephyr sandbox, cleaned up by killing the process directly rather than unlocking it; the idle-timing mechanism itself was separately confirmed live by swapping in a throwaway `xautolock` instance with a harmless one-line-file locker in place of the real one, watching it fire after its 1-minute threshold, then restoring the real instance — the actual account password was never needed or used anywhere in this process.
- Coupled the stay-awake toggle to the idle lock. These were initially independent: `xautolock` determines idle time via the X Screen Saver *extension* (confirmed via `ldd` showing it links `libXss.so.1` and calls `XScreenSaverQueryInfo`), which keeps counting regardless of whether `xset`'s own screensaver/DPMS blanking is on or off - so turning on stay-awake to e.g. watch a video without touching the mouse would still get the screen locked out from under it once xautolock's timer elapsed. Fixed by having the stay-awake toggle also send `xautolock -disable`/`-enable` (an IPC message to the already-running instance, no restart needed) alongside its existing `xset` calls. Verified live with the same throwaway-instance technique as above: confirmed a test instance's 1-minute timer did *not* fire while disabled, across a full 4-minute idle-polling window (this session's own active use of the machine kept resetting real idle time to near-zero throughout, which is exactly the scenario this fix targets); `-enable` uses the identical IPC mechanism in reverse and follows directly, though it didn't get its own independent live-fire confirmation in this session for the same reason (never a continuous idle stretch to test against) - worth a quick sanity check next time the machine is genuinely left idle with stay-awake off.

## Backlog — discussed, not started

- **True live drag-and-drop retiling.** Other windows should visibly reshuffle in real time while a window is being dragged over them, not just snap into place on release. This is genuinely new work — even Hyprland doesn't fully do this today.
- **Bundled compositor.** Blur, shadows, and real anti-aliased rounded corners via XComposite/XDamage + GLX/EGL, likely adapting picom's (MIT-licensed) blur/rounded-corner shader code. (Animations and basic X-Shape-based rounded corners already work today without a compositor — this is about blur/shadows specifically, plus a visual upgrade to rounding.) This is the single biggest remaining piece of work and isn't sequenced or scoped yet.
- **GUI settings app, full WM config.** The bar's own module config now has a GUI (see Done above); `hypr.conf` itself (keybinds, window rules, gaps/borders, etc.) is still hand-edit-only. Extending the GUI to cover that is still deferred until just before release.
- **Dock.** A macOS/Plank-style app dock — pinned + running-app icons, click to launch/focus. Not scoped yet.
- **Bar visual fixes.** Icons, layout, and general polish pass on the Quickshell bar. Includes: the "hidden tray" overflow flyout (`Overflow.qml`) currently opens screen-centered (via the same `windowrule=center` trick the launcher uses) — should instead anchor directly below the chevron icon that opened it, like a real dropdown.
- **Volume/brightness OSD.** A transient on-screen popup when volume/brightness keys are pressed. The volume module and Pipewire wiring already exist in the bar; this is mostly new UI.
- **Notification daemon.** No popup notification system exists yet — `screenshot.sh`'s `notify-send` call is currently a no-op unless something's listening for it.
- **MPRIS "now playing" widget.** Bar module showing/controlling whatever's playing (Spotify, browser media, etc.) — standard in Noctalia/DankMaterialShell-style shells.
- **Clipboard manager.** Clipboard history with a rofi-style picker.
- **Wallpaper picker/rotation.** Wallpaper is currently a single static `xwallpaper` call in `exec-once`.
- **Quick settings panel.** A single flyout (WiFi/Bluetooth/DND/brightness/volume) rather than a separate bar module per thing — the direction Noctalia/DankMaterialShell actually go, and it'd tie together the notification daemon's DND, a future Bluetooth toggle, and brightness in one place instead of three.
- **Screen recording.** Natural pair with `screenshot.sh` — same ffmpeg-family tooling, just recording instead of a single frame.
- **Night light / color temperature.** Redshift-style time-of-day blue light filter.
- **Bluetooth applet.** Toggle/pair devices from the bar.
- **Keybind cheat-sheet overlay.** Press a key, see all current keybinds — useful once the binds list grows.
- **First-run setup + config export/import.** A different kind of item than the rest — about *shipping* the project rather than day-to-day use. This project's own roadmap already targets a public release (final name TBD), but there's currently no path for someone else to pick this up cleanly beyond hand-copying dotfiles.
- **Fullscreen rule for non-Steam-launcher games.** Lutris/Heroic don't relabel `WM_CLASS` the way Steam does (no `lutris_*`/`heroic_*` equivalent), so the one-rule-covers-everything trick doesn't carry over. Need to test an actual Lutris/Heroic game to find out whether it already goes fullscreen on its own (via its own EWMH fullscreen request, a separate pre-existing code path) or needs a per-game rule. Also worth testing whether adding a Lutris/Heroic game to Steam as a non-Steam shortcut and launching it through Steam picks up the same `steam_app_*` class (likely, since that's Steam's own overlay/launch wrapper doing the relabeling — but unconfirmed).
