# Roadmap

Tracking what's done, what's planned, and what's still undecided for this fork.

## Beta target

Aiming for a beta/0.1 release as early as next weekend (no hard deadline — that's an earliest-case, not a commitment). The items marked **[Beta blocker]** in the backlog below are what's actually standing between "works great on this one machine" and something a stranger could reasonably install; everything else in the backlog (compositor, MPRIS, calendar flyout, etc.) is normal post-beta polish, not something a 0.1 needs.

## Done / working

- Dynamic tiling (dwindle + master) — inherited from upstream Hypr, unchanged
- Multi-monitor support — verified end-to-end (bar on every screen, correct per-monitor workarea reservation)
- Workspaces — global pool model; switching pulls a workspace to the focused monitor
- Built-in status bar removed in favor of an external EWMH shell (Quickshell)
- Quickshell rofi-style app launcher (usage-sorted results, icons)
- Quickshell bar (workspaces, clock, system tray, CPU/GPU temp, network status, volume)
- Audio (pipewire / pipewire-pulse / wireplumber) autostart on session launch
- Window rules extended with `title:` matching (upstream Hypr only had `class:` / `role:`)
- Fullscreen window rule for Steam games — confirmed working live on two different games. The mechanism turned out to already be fully implemented upstream (`windowrule=fullscreen,class:...`), just undocumented. Steam sets `WM_CLASS` to `steam_app_<appid>` for any game it launches (native or Proton/Wine), so `windowrule=fullscreen,class:^steam_app_.*$` covers a user's whole Steam library with one rule — activated as the default in both the example config and the user's own.
- Launcher positioning — added a new `center` window rule (reuses the existing dialog/modal auto-centering math, now available to any window via config) and applied it to the launcher; verified it lands pixel-exact in the center of the screen
- Animations fix — the animation speed formula (`1/DELTA`) used an integer-truncated millisecond delta; any two ticks landing under 1ms apart truncated to exactly `0`, causing a division-by-zero (infinite speed) that silently stalled that frame. Measured this actually happening (~1 in 221 idle ticks). Switched to a fractional-millisecond delta; confirmed empirically over hundreds of ticks that the stall case no longer occurs.
- Raised the default animation speed to near-instant (`speed`/`window_resize_speed` both 5→20, now equal) per feedback, updated everywhere a default lives (in-code fallback, autogenerated first-run config, example config) so this is the out-of-the-box experience, not just a personal tweak.
- Launcher auto-focus — floating windows (launcher, dialogs, etc.) never actually got X11 input focus from the WM on creation, only tiled windows did; you had to click in manually. Fixed and verified live (docks/panels correctly excluded, so the bar doesn't steal focus).
- Fixed a near-freeze on launching a game: `_NET_WM_STATE_FOCUSED` was appended to a focused window's state property on every dirty-refresh tick with no dedup, growing unbounded for any window that stays busy/dirty while focused (exactly what a game does). Same bug family as the earlier `_NET_WORKAREA`/RandR loops. Verified fixed under a forced stress test (40 rapid dirty cycles → still exactly one entry).
- Fixed focus-stealing (confirmed resolved live, not just in sandbox testing): launching a game and clicking away to another window would immediately snap focus back to the game. Took five attempts to actually nail: a 1s cooldown broke because the real reclaim happened 7+ seconds later; tracking "the specific window the user moved away from" broke because `eventEnter` fires on every window the pointer passes through en route, not just where it settles; the "does current focus belong to the user" redesign still failed live because it explicitly trusted EWMH's own source==2 ("explicit user action") indicator - confirmed via diagnostic logging that Wine/Proton sends exactly that value for its own internal reclaims, making the trust carve-out a complete no-op against the real culprit; one more asymmetry bug (a user hover into an already-focused-for-other-reasons window wasn't upgrading its status) surfaced during re-verification. Final version trusts no EWMH source value at all - only real clicks/hovers count as user-initiated. The live session's own log now shows real reclaim attempts from the game being rejected during actual gameplay, and the user confirmed focus behaves correctly.
- Bug fixes along the way: missing `xcb-util` build dependency, dock/workarea reservation race at map time, an EWMH `_NET_WORKAREA` infinite-loop freeze, a RandR screen-change notification feedback loop, and a broken session launcher that was silently running a stale system-wide binary instead of the real one
- Fixed popup/dropdown menus instantly closing on click or hover (reported live via Zen Browser's bookmark folder menus, "like a double click really fast"). `eventEnter()`'s fallback for a never-before-seen window unconditionally tried to manage and focus it, unlike `eventMapWindow()` which already skips override-redirect windows via `shouldBeManaged()` — toolkits create menus/dropdowns override-redirect specifically so the WM leaves them alone, and stealing focus the instant the mouse entered one made the toolkit immediately dismiss it. Reproduced end-to-end in a Xephyr sandbox against a real Zen Browser instance (clicking a bookmark folder, then hovering an entry inside it to open a nested tooltip) before and after the fix to confirm it.
- "Stay awake" toggle — a bar icon (coffee cup) that toggles X11 screensaver/DPMS blanking on/off via `xset`. No external tool (`caffeine`, etc.) was worth pulling in: this WM runs no idle-lock/screensaver daemon at all (no `xautolock`/`xss-lock`, nothing under OpenRC), so there's no DBus screensaver service for such a tool to talk to anyway — `xset` is the whole mechanism regardless. State lives in a shared `StayAwakeState` singleton so all monitors' bars agree, since DPMS/screensaver state is global to the X server, not per-monitor. Hit and fixed one bug along the way: attaching a `QtQuick.Controls` `ToolTip` (as an attached property) to the same `Item` as a click-handling `MouseArea` silently ate the click events — confirmed via a `console.log` in `onClicked` never firing even though the icon's hit-region was pixel-verified correct; removing the `ToolTip` fixed it immediately. Verified live: clicking each monitor's icon toggles real `xset` DPMS/screensaver state and all three bars' icons stay in sync.
- Configurable bar modules + a "hidden tray" overflow flyout. Hand-edited at `~/.config/quickshell/modules.json` (JSON, not TOML — Quickshell has no TOML parser but reads JSON natively via `JsonAdapter`), hot-reloaded live (no `qs` restart). Each of the 7 status modules (kernel/cpu/cpuTemp/gpuTemp/network/volume/stayAwake) gets `enabled` (on/off), `screens` (`"all"` / `"primary"` / an array of exact RandR output names), and `tray` (`false` = shown inline in the bar as today; `true` = still active, but tucked into a "..." flyout instead of taking up bar space). Checked Noctalia Shell and DankMaterialShell (both Quickshell-based) for prior art first: neither has the "active but tray-hidden" third state at all, just enabled/disabled — this is a genuine addition, not a port. Adapted Noctalia's simpler `enabled` + per-monitor-match TOML model over DankMaterialShell's much heavier full-GUI-settings-app approach. The flyout itself (`Overflow.qml`) needed the same `windowrule=float,title:...` / `windowrule=center,title:...` treatment the launcher already needed — Quickshell's `FloatingWindow` doesn't self-position under this WM by default, it gets auto-tiled like any other window unless a window rule says otherwise. Verified live: toggling `tray` in the JSON hot-swaps a module between the bar and the flyout with no restart, the flyout opens correctly sized and floating (not tiled), and clicking a module inside the flyout (tested with stayAwake) drives the same shared state a bar-inline instance would.
- GUI settings window (`Settings.qml`, gear icon in the bar) for the same `modules.json` the point above covers — a scoped-down first slice of the deferred full GUI settings app, not the whole WM config (that stays hand-edit-only in `hypr.conf` for now). Per-module Enabled / Screens (All or Primary — pinning to specific monitors by name is still JSON-only) / In-tray toggles, built from plain `Rectangle`/`MouseArea` rather than `QtQuick.Controls` (given the `ToolTip` bug found while building the stay-awake toggle, stuck to the pattern already proven reliable in this codebase). Writes go through the same `FileView`/`JsonAdapter` `ModulesConfig` already used for reading, via full-object reassignment (`Object.assign`) rather than in-place mutation, since QML only notices property *assignment*, not a nested object's field changing — confirmed in-place mutation would have silently failed to persist or update any binding. Verified live end-to-end: toggling a module's tray switch in the GUI immediately updates the bar, the flyout, and the on-disk JSON.
- Idle-based screen lock. `xautolock` (idle timer, `exec-once` in `hypr.conf`) driving `betterlockscreen` (a wrapper around `i3lock-color`, both already installed) as the locker, plus a manual `SUPER+L` keybind. No systemd/logind on this box, so `xss-lock` — which leans on logind's Lock/Unlock DBus signals — wasn't the right fit; `xautolock` has no such dependency. Locks after 10 minutes idle (matching the default DPMS timeout) with the desktop wallpaper blurred behind the prompt, cached once via `betterlockscreen -u <path> --fx blur`. Hit one gotcha: `betterlockscreen -l` takes exactly one effect name matching a cached variant, not a comma list — `-l dim,blur` silently fell back to the plain, unblurred image since "dim,blur" isn't a real cached name (confirmed by checking `~/.cache/betterlockscreen/current/`, which only ever holds one file per single effect, never a combined one). Verification was necessarily two-tier given a real i3lock unlock needs the actual account password, which nothing here can supply: the visual rendering (wallpaper/blur, clock, greeter text) was confirmed in a Xephyr sandbox, cleaned up by killing the process directly rather than unlocking it; the idle-timing mechanism itself was separately confirmed live by swapping in a throwaway `xautolock` instance with a harmless one-line-file locker in place of the real one, watching it fire after its 1-minute threshold, then restoring the real instance — the actual account password was never needed or used anywhere in this process.
- Coupled the stay-awake toggle to the idle lock. These were initially independent: `xautolock` determines idle time via the X Screen Saver *extension* (confirmed via `ldd` showing it links `libXss.so.1` and calls `XScreenSaverQueryInfo`), which keeps counting regardless of whether `xset`'s own screensaver/DPMS blanking is on or off - so turning on stay-awake to e.g. watch a video without touching the mouse would still get the screen locked out from under it once xautolock's timer elapsed. Fixed by having the stay-awake toggle also send `xautolock -disable`/`-enable` (an IPC message to the already-running instance, no restart needed) alongside its existing `xset` calls. Verified live with the same throwaway-instance technique as above: confirmed a test instance's 1-minute timer did *not* fire while disabled, across a full 4-minute idle-polling window (this session's own active use of the machine kept resetting real idle time to near-zero throughout, which is exactly the scenario this fix targets); `-enable` uses the identical IPC mechanism in reverse and follows directly, though it didn't get its own independent live-fire confirmation in this session for the same reason (never a continuous idle stretch to test against) - worth a quick sanity check next time the machine is genuinely left idle with stay-awake off.
- **Renamed the project: Hypr → ZarisWM** (short form **Zaris** for directory names, binary names, etc.). Name landed after several rounds: an earlier candidate, **Xobra** (X11 + the "Cobra" handle nod), was dropped once the goal of eventual use by others (not just personal use) came into focus — reviewing how established WMs are named (Hyprland, Sway, i3, bspwm, dwm, qtile, awesome) showed none of them tie the name to the maintainer's personal handle, which argued against **croXeyeWM** too (a second candidate, more directly tied to the "crosseyedCOBRA" handle). Zaris was checked clean against GitHub, npm, PyPI, and crates.io (crates.io's API 403's on every query from this environment regardless of name, so that check is inconclusive across the board, not a Zaris-specific gap) — the only exact-name GitHub hits are a handful of inactive, 0-star placeholder repos. Execution happened in two passes: an initial commit covered the CMake project/target name (lowercase `zaris`), EWMH `_NET_WM_NAME`, log messages, config path (`~/.config/zaris/zaris.conf`), log path (`/tmp/zaris/`), example config/desktop files, README, CONTRIBUTING.md, and issue templates; a follow-up swept the repo for what that pass missed — leftover `Hypr` strings in `example/zaris.desktop`'s internal fields (`Name=`/`Exec=`/`TryExec=`/etc.), a VS Code launch path, a config comment, the `pkill`/"exit Hypr" keybind-hint strings, a legacy `WM_NAME` placeholder in `windowManager.cpp`, and the internal `HYPRATOMS`/`HYPRATOM` EWMH-atom-map code symbols (renamed to `ZARISATOMS`/`ZARISATOM`, rebuilt clean to confirm). Also renamed everything outside version control: the local repo directory, the GitHub repo itself, `~/.config`, both the per-user and system-wide installed binaries, and the LightDM session entry — old `Hypr`-named copies of all of these were confirmed removed after the switch. `Hyprland` references (the separate, actively maintained Wayland compositor by the same original author) were deliberately left alone throughout, as was the README's fork-attribution mention of the original Hypr project — both are accurate references to real external projects, not this project's own branding.
- **Notification daemon.** `screenshot.sh`'s `notify-send` call (and anything else on the system that uses it) was a no-op with nothing listening on `org.freedesktop.Notifications`. Rather than build one in QML, wired up `dunst` (already installed, and `~/.config/dunst/dunstrc` already existed pre-themed to match this shell's palette exactly — a carryover from the old qtile setup) via `exec-once=dunst` in zaris.conf. Verified live end-to-end with `notify-send` and a screenshot: themed popup renders correctly top-right, doesn't get tiled/mismanaged by the WM (dunst's popups are override-redirect, which `shouldBeManaged()` already skips — same mechanism as the earlier Zen Browser dropdown-menu fix).
- **Volume OSD.** Transient popup on volume up/down/mute, driven by new `OSD.qml`/`OSDState.qml` plus `~/.config/zaris/osd-volume.sh` (adjusts the default sink via `wpctl`, then reports the result to the OSD over Quickshell's IPC: `qs ipc call osd volume <percent> <muted>`) bound to the `XF86Audio*` keys in zaris.conf. Auto-hides ~1.5s after the last call. Verified live: raise/lower/mute all show the correctly themed popup with the right percentage/muted state, and it disappears on schedule. Brightness was scoped out for now — this box is a desktop with no `/sys/class/backlight` device and no `ddcutil` installed, so there's nothing for `XF86MonBrightness*` to actually drive; `OSDState`/`OSD.qml` already support a `"brightness"` kind for whenever that's relevant on different hardware.
- **Bar visual fix: flyout anchoring.** The "hidden tray" overflow flyout (`Overflow.qml`) used to open screen-centered. Investigated having Quickshell position it directly (compute the chevron's global coordinates in QML, set them on the window) — turned out to be impossible: Quickshell's `FloatingWindow`/`WindowInterface` exposes `width`/`height` but no `x`/`y` at all (confirmed via its qmltypes; this is a real cross-platform constraint, not a missed API, since Wayland compositors don't let clients self-position either), so this had to be done WM-side instead. Added a new `topright <marginX> <marginY>` windowrule (`src/events/events.cpp`, `src/config/ConfigManager.cpp`) that positions a floating window relative to its monitor's top-right corner, computed from the monitor geometry and the window's own already-known size — the same pattern the existing `center` rule already uses, just anchored to a corner instead of the middle. Also moved the "more" chevron to be the last (rightmost) bar icon in `Bar.qml` (it previously sat before the screenshot/power/settings icons), so the top-right anchor actually lands under it. Built and installed the new binary; taking effect requires a WM restart (full logout, since this WM has no soft-restart/live-reload of its own binary — only the config file hot-reloads), deliberately deferred rather than done mid-session.
- **[Beta blocker, done] Shipped the Quickshell shell config in version control**, as a new top-level `shell/` directory (same repo, not a companion repo — chosen because the shell is tightly coupled to Zaris-specific window rules like `topright`, added this session specifically because the shell needed it, so keeping WM and shell changes in the same commit history matters more than clean separation would). `shell/` holds `quickshell/` (all the QML, `qmldir`, `modules.json`), `zaris/` (`zaris.conf` paired with this shell, `start-zaris.sh`, and the `powermenu.sh`/`screenshot.sh`/`osd-volume.sh` scripts), `dunst/`, and `rofi/` (the power menu's theme) — see `shell/README.md` for install steps and the full runtime dependency list. Auditing what a fresh install would actually need surfaced two real bugs along the way, both fixed: `Bar.qml` loaded its logo icon and screenshot script from `~/.config/qtile/...` (the old, unrelated qtile setup this WM replaced — a fresh install without that directory would have a broken logo and a dead screenshot button), now moved into the shell bundle itself (`quickshell/assets/artix.svg`, `zaris/screenshot.sh`); and `zaris.conf` had a stale leftover `exec-once=qs -c` (missing its required config-name argument, logging a `--config: 1 required TEXT missing` error every single boot) left over from before a later line replaced it with the correct `qs -d` invocation — removed. Confirmed both fixes live (rebuilt/reloaded, screenshot and logo click both still work). This is meant as the shipped *default* a future first-run wizard (see Backlog) customizes from, not the wizard itself.
- **Genericized the shipped default config** (first slice of the "hone the default" beta blocker below — the rest, bar polish and the dock, is still open). Found a real robustness bug while at it: `zaris.conf`'s `qs -d` (the bar/launcher) was chained after monitor setup and wallpaper via `sh -c '... && ... && qs -d'`, so if either of the first two ever failed, the whole shell silently never launched — split into independent `exec-once` lines so the bar always comes up regardless. For the live config (this machine), kept the real 3-monitor `xrandr` setup and personal wallpaper, just decoupled from the bar's own launch. For the shipped `shell/` copy specifically: dropped the personal 3-monitor `xrandr` call entirely (redundant anyway — `start-zaris.sh` already applies monitor layout before ZarisWM even connects, which is the correct place for it and was already running first regardless), replaced the hardcoded personal wallpaper path with a solid color matching `Colors.qml`'s own `bg` via `xsetroot` (no assumption of a specific image existing), and cleaned up several comments/docs that referenced "the old qtile setup" or instructed keeping colors "in sync with qtile's config.py" — accurate history for this machine, actively misleading for someone with no qtile config to sync with. Also documented (rather than silently removed) a harmless duplicate keybind (`SUPER+C` and `SUPER+Q` both bound to `killactive`) that had accumulated undocumented.
- **Swapped the screen locker from `betterlockscreen`/`i3lock-color` to plain `i3lock`.** The blurred-wallpaper lock screen (see the idle-lock entry above) depended on `betterlockscreen`, which is AUR-only on Arch and doesn't exist in Debian's repos at all — not viable as a cross-distro default. Checked all three target ecosystems directly (Arch/pacman via `pacman -Si` on this machine, Debian/apt via real apt metadata on a Devuan VM, Fedora/dnf via packages.fedoraproject.org) and found `i3lock` is the only screen locker packaged natively on all three — `slock` is missing on Debian, `i3lock-color`/`betterlockscreen` aren't packaged anywhere except the AUR, `physlock` is AUR-only on Arch. Traded away the blur/theming for that portability: `i3lock` has none built in. `zaris.conf`'s idle-lock `exec-once`, its `SUPER+L` keybind, and `powermenu.sh`'s Lock option all updated to call `i3lock` directly instead. Left a note in `zaris.conf` for anyone who wants the blur back later — it'd need a small vendored script (screenshot + blur, then hand off to `i3lock`), since no distro packages that combination as a single thing. See `DEPENDENCIES.md` for the full cross-referenced locker comparison.
- **Swapped the idle-lock timer from `xautolock` to `xss-lock`.** Same portability motivation as the locker swap above: `xautolock` isn't packaged for Debian under any name, and looks AUR-only on stock Arch too (only official via Artix's own `galaxy` repo); `xss-lock` is confirmed official on Arch, Debian, *and* Fedora. Real mechanism difference: `xss-lock` has no `-time` flag of its own — it fires off the X screensaver extension's own activation event instead, so the idle timeout now lives in the X server's screensaver timer (`xset q`) rather than a dedicated option, and it additionally listens for logind's Lock signal (elogind reimplements this, already a dependency here for the power menu's `loginctl` calls), so a suspend/lid event or manual `loginctl lock-session` locks too — `xautolock` never had that. Verified end-to-end in a Xephyr sandbox that `xss-lock -- i3lock` correctly spawns `i3lock` on a forced screensaver-activation event. One knock-on simplification this enabled: the stay-awake toggle's `xset s off` already fully suppresses screensaver activation (confirmed via `xset q` showing `timeout: 0` afterward), and `xss-lock` can't fire without that event, so the separate `xautolock -enable`/`-disable` IPC call the previous setup needed (see the "Coupled the stay-awake toggle" entry above) is gone entirely — `StayAwake.qml` simplified accordingly. Caveat worth being upfront about: the actual auto-fire-vs-suppressed timing comparison didn't reproduce cleanly under Xephyr (nested X servers are known to be unreliable about real idle-timer counting, separate from the forced-activation test which did work), so that specific piece rests on X11's well-established core-protocol semantics for `timeout: 0` rather than a clean sandboxed reproduction — worth a real live confirmation next chance.
- **Built Quickshell from source on Debian, closing the biggest remaining dependency-list gap.** `quickshell` itself was the one non-negotiable shell dependency with no Debian package at all — everything else has a distro-native answer, but without Quickshell the shell simply doesn't run. Read through Quickshell's own `BUILD.md` for its real dependency list and CMake feature flags, then verified an actual from-scratch build end-to-end on a real Devuan Excalibur VM: apt-only build deps (`qt6-base-dev`, `qt6-declarative-dev` + its private-headers package, `qt6-shadertools-dev`, `libdrm-dev`, `spirv-tools`, `libcli11-dev`, `libpipewire-0.3-dev`, `ninja-build`), a `cmake -GNinja` configure with the Wayland-specific features (`WAYLAND`, `WAYLAND_WLR_LAYERSHELL`, `WAYLAND_SESSION_LOCK`, `WAYLAND_TOPLEVEL_MANAGEMENT`, `SCREENCOPY`) and the unrelated `HYPRLAND`/`I3` IPC integrations all turned off (Zaris is X11-only and isn't Hyprland or i3), plus `CRASH_HANDLER`/`USE_JEMALLOC` off since neither's needed and `cpptrace` isn't packaged for Debian either. Configured clean, built clean (592/592), installed clean, and `qs --version` ran successfully afterward — confirmed Quickshell's own CMake install rules create the `qs` → `quickshell` symlink automatically, matching exactly what `zaris.conf`'s `qs -d` invocation expects. Automated as a new `quickshell` step in `contrib/devuan-bootstrap.sh`, which the `nix` step's messaging previously pointed to instead — Nix is now only needed there for a Nerd Font, not Quickshell itself. See `DEPENDENCIES.md`'s "Building Quickshell from source" section for the full recipe.
- **Built the app dock.** `Dock.qml` + `DockConfig.qml` (config: `enabled`, `mode`, `pinned`, backed by `~/.config/quickshell/dock.json`) + `DockIcons.qml` (the icon row) + `DockLauncherIcon.qml` (a static, always-leftmost icon opening the same launcher the bar's logo does). Pinned apps come from a right-click "Pin to Dock"/"Remove from Dock" themed confirmation dialog (`PinDialog.qml`/`PinDialogState.qml`, styled like OSD/Settings, anchored bottom-center just above the dock via the new `bottomcenter` windowrule below) — reachable from either a Launcher result or an existing dock icon. Running apps are tracked via `wmctrl -lx` polled on a timer (same approach as `Workspaces.qml`, since Quickshell has no generic X11 window-list service) and matched to installed `.desktop` entries primarily via `entry.startupClass` (the freedesktop-standard `StartupWMClass=` field, read by Quickshell's `DesktopEntries`), falling back to exact-token comparison against the entry's id/name if unset — never a loose substring match, which turned out to matter: an early substring-based heuristic let a generic WM_CLASS fragment like `"com"` (from a web-app window whose `--class` embeds a domain) false-positive-match a completely unrelated app's id that merely happened to contain the same fragment, showing that app's icon instead. Two modes, both with a Settings toggle: "reserved" (a `PanelWindow`, permanently reserves space like the bar) and "floating" (a `FloatingWindow` anchored via `bottomcenter`, no reserved space, windows can tile underneath). Deliberately does not try to disambiguate two windows that both genuinely report the same WM_CLASS (confirmed live: two WebApp Hub-created web apps sharing one non-isolated Chromium process/profile can end up with the second window inheriting the first's `--class` at the OS level - fixed on the WebApp Hub side, per-webapp process isolation, not something the dock can distinguish since X11 itself can't tell the windows apart at that point).

  Along the way, found and fixed three real, previously-dormant WM bugs that nothing had ever exercised before a dock could be toggled on/off and resized at runtime: (1) `ConfigManager.cpp`/`events.cpp` needed a new `bottomcenter <marginY>` windowrule (mirroring the existing `topright`) for the floating mode's positioning. (2) Floating-window position/size rules (`topright`/`bottomcenter`/`center`/`move`/`size`) only ever apply the *first* time a given window is mapped (gated by `getFirstOpen()`) - fine for every other floating window in this shell since their target position is a fixed formula that never needs to change after first open, but the pin dialog's rule got changed (center → topright → bottomcenter) after it had already opened once, so it stayed stuck at a stale position until the next full `qs` restart created a genuinely new window. (3) `eventUnmapWindow` unconditionally skipped `closeWindowAllChecks` for any dock-type window, which meant hiding one (the dock's own `enabled` toggle) never released its reserved space - nothing had ever unmapped a dock-type window at runtime before, since the bar has no on/off switch. Also found and fixed: `eventConfigure` only ever pushed a resized floating window's new geometry to the X server (`xcb_configure_window`) for dock-type windows via `recalcAllDocks()` - a *non*-dock floating window (the dock's own "floating" mode) that resizes itself post-map had its internal bookkeeping updated with nothing ever applied on screen, so it never visually changed size, while "reserved" mode (dock-type, already going through `recalcAllDocks()`) resized correctly the whole time.

  Also traced and fixed a real, previously-unconfirmed pre-existing bug while debugging why the dock and secondary-monitor bars intermittently didn't appear at all after a fresh boot/login - documented in the next entry below.
- **[Beta blocker, done] Root-cause the dock/workarea reservation sometimes failing at boot.** Root cause confirmed with real evidence, not just a working theory anymore: `/tmp/zaris/zaris.log`'s `New dock created` entries showed, across multiple fresh logins, that secondary-monitor bars (and the app dock) were never created at all - not mispositioned, not missing their reservation, genuinely absent, while the primary monitor's bar came up fine every time. `qs kill` + relaunch reliably fixed it every single time it was reproduced. This points at Quickshell's own screen enumeration (`Variants { model: Quickshell.screens }` in `Bar.qml`), not the WM's dock-handling: Quickshell reads the screen list once at its own startup, and if RandR hasn't finished settling a multi-monitor reconfiguration at that exact instant, it undercounts and never self-corrects for the rest of that process's life - only a full restart re-queries and gets the real count. `start-zaris.sh`'s own `xrandr` call finishing doesn't guarantee the X server's internal state has fully propagated to other clients by the time `zaris.conf`'s `exec-once=... qs -d` runs moments later.

  Fix: `zaris.conf`'s `qs -d` line now polls `xrandr --query`'s connected-monitor count, waiting for it to read the same value on two consecutive checks (0.3s apart, capped at 6s) before launching Quickshell, rather than assuming RandR is settled the instant the WM hands off to `exec-once`. Falls through and launches anyway after the timeout if the count never stabilizes. Confirmed working on a genuine fresh reboot (not just a `qs`-only restart): `zaris.log`'s `New dock created` entries showed all three monitors' bars plus the app dock created correctly on the very first attempt, no manual intervention needed - the first time all session a cold boot has come up clean on its own.

## Noctalia design-system port — running list

Investigated whether Noctalia (a Quickshell-based shell, screenshotted by the user as a design target for the settings app) could be adopted wholesale to save time. Current Noctalia (`noctalia-dev/noctalia`, main branch) turned out to be a full C++/Qt rewrite (215 `.cpp` files vs. 26 `.qml`), tightly coupled to their own custom Wayland compositor ("Umbriel") - not portable to an X11 WM's plain-QML-on-Quickshell shell at all. `noctalia-dev/noctalia-qs` (their toolkit repo) turned out to just be an archived fork of Quickshell itself with one Wayland-only compositor-protocol patch - irrelevant to X11, no value.

However, the **pre-rewrite `v4.7.7` tag** of `noctalia-dev/noctalia` is a genuine MIT-licensed, plain-QML Quickshell shell - same architecture as Zaris. Of its 418 QML files, only ~43 (~10%) import Wayland/compositor-IPC-specific Quickshell modules (`Quickshell.Wayland`, `Hyprland`/`Sway`/`I3` IPC) and can't be ported; the rest (widgets, styling, generic services) has no such coupling. Per explicit user direction, the approach is to pull as much of that ~90% as reasonably adaptable now, rather than pre-filtering for "do we need this yet" - reassessing what to keep/drop happens after, not before, porting. See `README.md`'s "Third-party code" section for the MIT attribution this carries.

**The actual end goal, stated explicitly by the user**: get Zaris's shell UI to visually match Noctalia v4.7.7 as closely as reasonably possible, then build new Zaris-specific features on top of that foundation - not port-for-its-own-sake. This is a three-phase effort, and the phases are sequenced deliberately rather than interleaved: **(1)** finish pulling the portable "ingredient set" first - the design tokens, color-role system, generic widget library, and portable services, all tracked below - **(2)** only after that set is more complete, do one cohesive pass rebuilding Zaris's *existing* widgets/screens (bar, dock, launcher, the individual status modules) to actually use those ingredients consistently, since Noctalia's own bar/dock/panel *composition* files are exactly the Wayland-coupled ones that can't be ported - the ingredients transfer, the assembly is still Zaris's own to (re)build, and porting the ingredients alone doesn't retroactively reskin anything already built with the older hand-rolled `Rectangle`/`Text` pattern - **(3)** new custom features on top of that unified foundation. Phase 2 hasn't started; only 3 toggles (`Settings.qml` x2, `BluetoothPanel.qml`) use the new `ToggleSwitch` component so far, everything else in the shell still uses the pre-port pattern.

  Zaris's own WM build now has the from-scratch verification treatment on **all three** of Arch, Debian, and Fedora: cloned fresh, `cmake` configured clean against exactly the documented package list for each (every `pkg_check_modules` module resolved, confirmed via `pkg-config --exists` before even trying), built clean, and produced a working, correctly-linked binary. One interesting non-issue surfaced there: the built binary's `ldd` output doesn't list `libxcb-ewmh.so` at all on Debian, unlike Arch's build — traced to Debian's toolchain linking with `--as-needed` by default, which drops the `DT_NEEDED` entry for `xcb-ewmh` since the codebase only uses its header (`#include <xcb/xcb_ewmh.h>`) for type/constant definitions and never actually calls any of its functions (confirmed via `grep`: the only `xcb_ewmh_*` match in `src/` is inside a comment). Harmless, not a missing dependency, just a tidier binary on Debian.

No package-name gaps found; `DEPENDENCIES.md`'s Fedora column needed no corrections. This closes the last piece of this item — all three distros now have a real, verified, from-scratch build, and there are no known gaps left anywhere in `DEPENDENCIES.md`. - **[Beta blocker, paused] Verify on a non-OpenRC (systemd) system.** Everything OpenRC-specific here looks like it was already written defensively rather than actually coupled to OpenRC: the `exec-once=pipewire`/`pipewire-pulse`/`wireplumber` lines are already documented as harmless no-ops under systemd's socket activation, `powermenu.sh` already calls `loginctl` (the actual systemd-logind tool — elogind just reimplements its interface for non-systemd boxes), and idle-lock now runs on `xss-lock` (see Done above), which does hook logind's suspend/lid signals via elogind's D-Bus reimplementation — already exercised on this OpenRC box since elogind is what's providing `loginctl` here too, so it's not an untested systemd-only path. The WM binary itself (pure XCB/X11) has no init-system awareness anywhere. So this is expected to already work unmodified on a systemd distro — but it's never actually been tried there, only ever run on this one OpenRC box. Needs one clean install on a systemd machine to confirm before calling anything beta.

  A Debian 13 VM (`debian13-zaris`) was mid-unattended-install for this when the verification pass was deliberately paused to prioritize the Noctalia design-system port instead — not abandoned, just deprioritized. The VM is left running (a local libvirt VM, no ongoing cost) in case it's worth resuming from where it was rather than starting over; the install had gone through one restart already (an initial "desktop" profile attempt was pulling in an unwanted full GNOME install, aborted in favor of a slimmer profile) and was still short of a DHCP lease over an hour in when paused, a genuinely slower run than the equivalent Fedora verification.
- **[Beta blocker, in progress] Hone the default config, bar, and dock into a clean out-of-the-box look.** The goal for beta isn't "everything customized" (that's what the first-run wizard below is eventually for) — it's a sensible, presentable, mostly-empty-desktop-with-good-bones default that someone can install and immediately configure from, rather than something that visibly reads as "someone else's dotfiles." The `zaris.conf`/`modules.json` review pass is done (see Done above), and the dock itself now exists (`Dock.qml`/`DockConfig.qml`/`DockIcons.qml`/`DockLauncherIcon.qml`/`PinDialog.qml`) — pinned + running apps, a static launcher icon, right-click pin/unpin via a themed confirmation dialog, reserved-space or floating modes with a Settings toggle for both, all confirmed working live. Still open: a visual polish pass on the bar itself (spacing/icons/layout) — the dock's own polish (sizing, icon matching) got plenty of attention already, but the bar hasn't had an equivalent pass yet.
- **True live drag-and-drop retiling.** Other windows should visibly reshuffle in real time while a window is being dragged over them, not just snap into place on release. This is genuinely new work — even Hyprland doesn't fully do this today.
- **Bundled compositor.** Blur, shadows, and real anti-aliased rounded corners via XComposite/XDamage + GLX/EGL, likely adapting picom's (MIT-licensed) blur/rounded-corner shader code. (Animations and basic X-Shape-based rounded corners already work today without a compositor — this is about blur/shadows specifically, plus a visual upgrade to rounding.) This is the single biggest remaining piece of work and isn't sequenced or scoped yet.
- **Security features.** Not scoped yet — worth a dedicated look at what's worth adding. Some starting points: whether the idle-lock/manual-lock screen can be bypassed via a WM keybind firing while `i3lock` holds its keyboard grab (should already be safe since the grab should take priority, but unverified); hardening how much trust the WM places in client-supplied EWMH hints (the focus-stealing fix already moved to trusting no `_NET_ACTIVE_WINDOW` source value at all, for exactly this kind of reason); and being upfront in the docs about what's simply inherent to X11's security model (any client can inspect/control any other client's windows, keystrokes, etc. — a real architectural difference from Wayland, not something a WM-level fix can paper over).
- **GUI settings app, full WM config.** `zaris.conf` itself (keybinds, window rules, gaps/borders, etc.) is still hand-edit-only - no GUI category exists for any of it yet. Extending the settings app to cover that (as new categories in the sidebar shell - see Done above) is still deferred until just before release.
- **Dock: launcher icon side setting.** A Settings GUI toggle for whether the dock's static launcher icon sits on the left or right end (currently hardcoded leftmost in `Dock.qml`). Not the launcher icon itself becoming reorderable/draggable - it stays a fixed anchor point either way, just configurable which end.
- **Calendar flyout on clock click.** Clicking the bar's clock should open a calendar right below it, similar to Noctalia. The clock sits centered in the bar, not at a corner, so this needs its own anchoring approach — the `topright` windowrule added for the overflow flyout only handles corner-anchoring; this would need something like a `topcenter`-style rule (or a more general "anchor under an arbitrary bar position" mechanism) computed the same WM-side way, since Quickshell still can't position its own windows.
- **MPRIS "now playing" widget.** Bar module showing/controlling whatever's playing (Spotify, browser media, etc.) — standard in Noctalia/DankMaterialShell-style shells.
- **Clipboard manager.** Clipboard history with a rofi-style picker.
- **Wallpaper picker/rotation.** Wallpaper is currently a single static `xwallpaper` call in `exec-once`.
- **Quick settings panel.** A single flyout (WiFi/DND/brightness/volume, plus folding in the existing Bluetooth and night-light toggles) rather than a separate bar module per thing — the direction Noctalia/DankMaterialShell actually go. WiFi and the notification daemon's DND aren't bar modules yet at all; Bluetooth and night light already are (see Done above) and would just move into this flyout rather than being built from scratch.
- **Screen recording.** Natural pair with `screenshot.sh` — same ffmpeg-family tooling, just recording instead of a single frame.
- **Keybind cheat-sheet overlay.** Press a key, see all current keybinds — useful once the binds list grows.
- **First-run setup wizard.** Now that `shell/` (see Done above) ships a working default, the end goal is a guided first-run flow that walks a new user through customizing it — which bar modules to show, what's tucked into the hidden tray, whether to enable the dock, etc. — rather than hand-editing `modules.json` and `zaris.conf`. Also where config export/import would live, for moving a tuned setup to another machine. Depends on the full WM-config GUI item above for the pieces that aren't already covered by the existing bar-module settings window.
- **Scratchpad / dropdown window.** A floating window (typically a terminal) bound to a key that instantly hides/shows rather than needing to be found/refocused normally - i3's scratchpad, or the dropdown-terminal patches common on dwm/bspwm. Popular enough to be worth having; scoped as a genuinely new WM-side mechanism (move-to-scratchpad + toggle-visibility on a designated window), not a windowrule tweak.
- **Sticky windows.** A window that stays visible on every workspace instead of belonging to just one (bspwm/i3) - useful for something like a music player or a notes window you always want at hand regardless of which workspace you're on.
- **Urgency hints.** A window demanding attention (e.g. an incoming chat ping) should flash its workspace indicator in the bar even while you're focused elsewhere (i3's urgency hint, sent via `_NET_WM_STATE_DEMANDS_ATTENTION`/`WM_HINTS` urgency bit) - the WM would need to pick up and expose that hint, and `Workspaces.qml` would need to react to it.
- **Workspace back-and-forth.** One keybind toggles between the current and the immediately-previous workspace (i3's `workspace back_and_forth`), rather than needing to remember and re-press the actual workspace number.
- **Smart gaps / smart borders.** Auto-hide gaps and/or the window border when only one window occupies the tiling area, restoring them the moment a second window is tiled alongside it (i3-gaps/bspwm staple) - purely a visual default that's easy to miss until you notice single-window layouts look unnecessarily inset.
- **Keyboard-driven resize mode.** A modal "resize" keybind state (press a key, then use arrow keys/hjkl to grow/shrink the focused window, escape to exit) as an alternative to mouse-drag-only resizing, matching i3's resize mode.
- **IPC/scripting interface.** i3 has `i3-ipc`/`i3-msg`, Sway has `swaymsg`, Hyprland has `hyprctl` - a socket-based protocol external tools and scripts can use to query window/workspace state and issue commands live, distinct from `zaris.conf`'s static config. Right now the only way anything (including Quickshell) talks to this WM is through config file rules - there's no live query-and-control path. Bigger, unscoped architectural work, not a quick add.
- **Portability of `shell/` to other X11 WMs.** A "super super long term" idea, explicitly not a design goal right now. Most of the shell's individual widgets/services (status modules, Bluetooth, MPRIS, the whole ported Noctalia ingredient set) only depend on generic X11/D-Bus/system services and would already work unmodified on any EWMH-compliant X11 WM. What wouldn't: every floating window's on-screen *position* (launcher, settings, OSD, dock's floating mode, etc.) relies entirely on Zaris's own custom windowrule system (`center`/`topright`/`bottomcenter`), and the bar/dock's rounded corners rely on Zaris's own X11 SHAPE-extension code applied to dock-type windows - neither exists on any other WM, so this exact config would render with square corners and misplaced floating panels elsewhere today. Making it genuinely portable would need either a fallback positioning/rounding layer built into the shell itself (not relying on the host WM at all), or equivalent hooks in whatever other WM it's asked to run under - neither attempted, both nontrivial.
- **Monocle/tabbed layout.** A third tiling layout alongside the existing dwindle/master, where one window fills the whole tiling area and the rest queue behind it, cycled via keybind (bspwm's monocle, i3's tabbed layout) - useful for terminal-heavy or single-focus workflows where dwindle/master's always-visible splits aren't wanted.
- **Session save/restore.** Reopen the same apps in the same workspace layout after a WM restart or reboot (i3-resurrect-style) - not scoped yet; would need to decide how much (just workspace/position, or actual app relaunch commands) is realistic to restore given arbitrary GUI apps don't have a generic "reopen with this exact state" mechanism.
- **Fullscreen rule for non-Steam-launcher games.** Lutris/Heroic don't relabel `WM_CLASS` the way Steam does (no `lutris_*`/`heroic_*` equivalent), so the one-rule-covers-everything trick doesn't carry over. Need to test an actual Lutris/Heroic game to find out whether it already goes fullscreen on its own (via its own EWMH fullscreen request, a separate pre-existing code path) or needs a per-game rule. Also worth testing whether adding a Lutris/Heroic game to Steam as a non-Steam shortcut and launching it through Steam picks up the same `steam_app_*` class (likely, since that's Steam's own overlay/launch wrapper doing the relabeling — but unconfirmed).
